Bits and bytes — the absolute foundation
Group 8 bits together and you get a byte — a byte can represent any number from 0 to 255 (since 2⁸ = 256 possible combinations).

Hexadecimal — why you see things like \x89
Writing byte values in plain decimal (0–255) is clunky to read in bulk, so programmers use hexadecimal (base 16) instead: digits 0-9 then a-f for 10-15. Two hex digits exactly represent one byte (since 16×16 = 256).

\x89 means "the byte whose value in hex is 89" — that's decimal 137. The \x is just Python's way of writing "the next two characters are a hex byte value" inside a string, e.g. b'\x89'.

So when I wrote the PNG signature as \x89PNG\r\n\x1a\n, that's 8 individual bytes:

8 Bytes :- \x89PNG\r\n\x1a\n

Byte 1 (\x89, decimal 137) — catches "7-bit" corruption.
A byte has 8 bits, giving values 0–255. Some very old text-transfer systems only bothered to send the lower 7 bits of each byte (values 0-127), because that's all plain ASCII text needs — they'd chop off the 8th bit ("high bit") thinking it was safe, since real text never used it. 137 is above 127, meaning its high bit is set to 1. If some old/buggy tool strips that high bit, byte 1 turns into a different value, and PNG readers can immediately tell "this file got mangled in transit" because the first byte doesn't match what's expected.

Bytes 5-6 (\r\n, i.e. CR then LF) — catches line-ending translation.     This is about how diff"end of line" in a text file:
- Old Mac: just CR
- Unix/Linux/modern Mac: just LF (\n)
- Windows: both CR and LF together (\r\n)
Historically, when sofmode" (assuming it'shuman-readable text), it would sometimes "helpfully" rewrite line endings to match the local OS's convention — e.g., turning \r\n into just \n, or vice versa. That's finPNG is binary data, not
text — if some careles "fixed" the lineendings, it would corrupt the image data. So the signature deliberately includes a \r\n pair right up front: if a tool has been silently doing this translation, this pair gets mangled, and you can detect the
corruption immediatelyew bytes.

Byte 7 (\x1a, decimal 26) — catches truncation, specifically on old DOS systems.
Ancient MS-DOS text files didn't reliably store their exact length — some programs, when displaying a text file, would just read bytes until they hit this specific byte (26, historically called "Ctrl-Z" or "SUB"), and treat that as "end of file, stop reading here," even if there was more data after it. By deliberately putting this byte in the signature, PNG guarantees: if some old DOS tool naively tries to type or display a PNG file thinking it's text, it stops right there instead of dumping garbage binary data to your screen. It's also a second truncation check — if a transfer got cut short exactly here, you'd notice.

Byte 8 (\n) — catches
Symmetric to bytes 5-6: this catches tools that go the other direction and insert/strip line feeds.

So the whole 8-byte siry byte is a deliberate booby-trap for a specific historical file-corruption bug, chosen by the PNG designers in the 1990s when file transfers between different systems were genuinely unreliable.

CRC (Cyclic Redundancy Check)
think of it as a fingerprint of a chunk of data. You run the data through a specific math formula and get back a 4-byte number. Whoever wrote the file computes this fingerprint and stores it. 
Whoever reads the file later recomputes the same fingerprint from the data they received — if it doesn't match the stored one, they know the data got corrupted somewhere along
 the way, without needing to know what changed, just that something did. It's the same idea as a checksum on a package label — cheap to verify, catches accidental corruption (not intentional tampering — that's what cryptographic hashes are for, a different concept).

2. Bresenham line + midpoint circle

Bresenham's line algorithm draws a line using only integer arithmetic — no floating point, no rounding errors. The trick: track an error term representing how far the ideal line has drifted from the current pixel row. 3. Perlin noise + fBm

Perlin noise is gradient noise: at each integer lattice point, assign a pseudorandom direction vector (not a value). For any query point, take the dot product of "vector from each of the 4 surrounding corners to the point" with "that corner's gradient" — this gives four numbers, one per corner. Blend them together using the quintic fade curve 6t⁵−15t⁴+10t³     instead of linear inteerpolation createsvisible creases at cell boundaries (its second derivative is discontinuous); the quintic curve has zero first and second derivative at the cell edges, so the result looks smooth under lighting too.            
fBm (fractal Brownian motion) just layers multiple octaves of this noise at different frequencies/amplitudes: Σ amplitude^i * noise(frequency^i * p). Low octaves give big rolling shapes (mountains), high octaves add fine detail (rocky texture). This is literally how most procedural terrain in games is built.

4. SDF primitives + smooth-min

A signed distance field is a function f(point) → distance to nearest surface, negative when inside the shape. sdCircle(p, r) = length(p) - r is the simplest example — trivially, distance from center minus radius. The   powerful part is compos two shapes (the point belongs to whichever is closer), and smin (smooth minimum) does the same thing but blends the seam organically instead of leaving a hard crease — controlled by a blend-width parameter k. This is how you get things like a mountain range that merges smoothly instead of terrain that looks like two shapes glued together.

4. What's an "octant" then?

Since one computed point gives you 8 points for free, you only ever need to compute 1/8th of the circle's points — the algorithm does real work for one slice, and the other 7 slices are just free mirrors.

Think of the circle like a clock face cut into 8 equal pie slices (each 45°, since 360° / 8 = 45°). Each slice is an octant. The algorithm computes one octant — conventionally the slice from straight up (12 o'clock, angle 0°) sweeping down to the 45° diagonal (roughly the 1:30 position). That's the arc where, as you move along it, x is always less than or equal to y.

Why stop at 45°? Because past that point, you'd just be computing the mirror image of pixels you already have — continuing would be redundant work.

5. Walking the octant: the decision parameter

Inside that one octant, here's the situation at each step: you know you're moving from left to right (x always increases by exactly 1 each step — that part's not a decision). The only question each step is: does y stay the same, or does y also decrease by 1?

- Moving only in x (y unchanged) → call this the "E" move (East)
- Moving in x and decreasing y → call this the "SE" move (Southeast)

To decide, the algorithm checks: between these two candidate pixels, which one is closer to where the true circle actually passes? It does this by testing the midpoint between the two candidates (hence the algorithm's name) against the circle equation x² + y² - r²:

- If that midpoint falls inside the true circle (the expression is negative) → the real curve is farther out than the midpoint → the "E" pixel is the better match.
- If the midpoint falls on or outside the true circle → the real curve has already curved inward → the "SE" pixel is the better match.

This test reduces to simple integer addition/subtraction updates each step (just like Bresenham's line — no floating point, no square roots, ever), tracked in a running value usually called p (the decision parameter).

7. Putting it together: from one octant to a full circle

For every (x, y) you compute in that octant, immediately plot all 8 mirrored points (this time adding the real center back in, cx, cy):

(cx+x, cy+y)   (cx-x, cy+y)   (cx+x, cy-y)   (cx-x, cy-y)
(cx+y, cy+x)   (cx-y, cy+x)   (cx+y, cy-x)   (cx-y, cy-x)

Do that for every point the loop produces, and you've drawn the entire circle outline — using nothing but integer addition and subtraction.

def midpoint_circle(cx, cy, r):
    1. Set x = 0, y = r, p = 1 - r.
    2. Start a results list.
    3. Plot all 8 symmetric points for the current (x, y) into results (add cx, cy).
    4. Loop while x < y:
         a. x = x + 1
         b. if p < 0: p = p + 2*x + 1   (E move, y unchanged)
            else:     y = y - 1
                      p = p + 2*x - 2*y + 1   (SE move)
         c. Plot all 8 symmetric points for the new (x, y) into results.
    5. Return results.
